# Battle Scars
_Non-obvious bugs, hard-won lessons. Date each entry. Remove when root cause is fixed._

- **[2026-05-07]** [bootstrap] `infrared_city_gis/__init__.py` calls `_ensure_deps()` (in `utils/deps_bootstrap.py`) at plugin load. It pip-installs `requests`, `numpy`, `shapely`, `pyproj`, `mapbox_earcut`, `structlog`, `infrared-sdk` if missing, reading from `requirements.txt`. **Two implications:**
  - `requirements.txt` MUST stay inside the shipped ZIP — the bootstrap reads it at runtime. If you ever exclude it from `release.yml`, the bootstrap silently does nothing.
  - plugins.qgis.org reviewers sometimes flag plugins that pip-install at runtime as a security concern. Be ready to explain it (numpy isn't reliably bundled with QGIS on Windows, mapbox_earcut needs native wheels). Long-term consider vendoring deps at CI build time instead.
- **[2026-06-30]** [bootstrap/uninstall] Deps used to install into `infrared_city_gis/thirdparty/` (inside the plugin folder). On **uninstall** QGIS deletes the whole plugin dir, but the loaded `numpy`/`mapbox_earcut` native extensions (`.pyd`/`.dll`) are **locked by the running process on Windows** → "folder in use", uninstall aborts. **Fix:** deps now install into the **QGIS profile dir**, outside the plugin folder, so uninstall never touches locked files. Layout: `<profile>/infrared_city_gis/deps-<hash>/`, where `<hash>` is a short order-independent SHA1 of the requirement specs (`_reqs_hash`). **Why the hash:** `_find_missing` only checks *importability*, not version — so a bumped pin (e.g. `infrared-sdk>=0.4.10` → `>=0.5.0`) reusing the same folder would never reinstall. A changed requirement set → new hash → fresh empty folder → correct versions installed; only the current `deps-<hash>` is on `sys.path`, so the stale set isn't even importable. `_cleanup_legacy_thirdparty()` removes the old in-plugin folder; `_cleanup_old_deps_dirs()` removes sibling `deps-*` from previous sets (both best-effort/`ignore_errors`, work on a fresh session because those paths aren't on `sys.path`). **Caveats:** (1) after uninstall the last `deps-<hash>` is orphaned in the profile dir — no QGIS uninstall hook + can't self-delete from `unload()` (runs on every shutdown/reload). (2) A dep version bump only takes effect after a QGIS **restart** — already-loaded C extensions can't be hot-swapped.

- **[2026-06-30]** [packaging] plugins.qgis.org (and security scanners) flag **hidden files** in the uploaded package. The release ZIP (`release.yml`) zips `infrared_city_gis/`, which used to include `infrared_city_gis/.gitignore` and `tests/fixtures/.gitkeep` (and the whole multi-MB `tests/` dir). **Fix:** the zip `-x` list now excludes `*/.*` (all hidden files at any depth) plus `infrared_city_gis/tests/*` and `.../test/*`; removed the now-redundant `.gitkeep` (the `fixtures/` dir is kept alive by its real fixtures). The CLAUDE.md local `zip` command mirrors this. Note: only files **inside** `infrared_city_gis/` ship — root `.flake8`/`.gitignore`/`.release-please-manifest.json` are never packaged.

- **[2026-09-29]** [pyarrow/shutdown] **QGIS SIGSEGVs on quit after a ground-material fetch.** Thread `EvntLoopCleanup`, `EXC_BAD_ACCESS` at `0x10` in `Aws::Utils::Logging::s_aws_logger_redirect_get_log_level` ← `s_aws_event_loop_group_shutdown_sync`, while the main thread is in `__cxa_finalize_ranges` ← `exit`. pyarrow (pulled in by the SDK's `[geodata]` extra) reads Overture from **S3**, and its AWS event loop must be finalized before static destructors run. pyarrow registers `atexit.register(ensure_s3_finalized)` for exactly this (`pyarrow/fs.py`), **but QGIS's embedded interpreter never runs atexit** — the app exits without finalizing Python, so the cleanup thread calls a logger C++ has already destroyed. **Fix:** `infrared_city_gis._finalize_arrow_s3`, connected to `QgsApplication.aboutToQuit`. NOT in `unload()`: S3 cannot be re-initialised once finalized (`ArrowInvalid: Attempt to initialize S3 after it has been finalized`, verified), and `unload()` also runs on a plugin reload — which would leave ground materials broken for the rest of the session. **Also worth knowing:** QGIS ships its own `libarrow.2200.dylib` while our deps dir loads `libarrow.2500.dylib`, so **two Arrow versions live in one process**. Not the cause of this crash, but it is the kind of thing to check first when Arrow misbehaves.

- **[2026-09-29]** [tiling/cost] The area tiler steps every **256 m** with 512 m tiles, so it never answers "1 tile" for a real selection: a 512×512 m box becomes **4** jobs, 513 m becomes **9**, 1024 m becomes **16** (measured against SDK 0.9.5rc7, pinned in `tests/test_single_tile_selection.py`). That is why a single tile is submitted through `analyses.execute` instead, and why the simulation dialog must NOT quote `preview_area()` for it — the tiler would over-quote by 4×. A single job also ALWAYS returns a 512×512 grid georeferenced from the polygon's SW corner outwards, so the polygon it is given has to be the full 512 m box or the selection ends up in the bottom-left of its own result.

- **[2026-09-29]** [ui/selection] **The picked BOX is stored, not the selection it highlighted.** Deriving the run polygon from the map selection was tried and reverted within a day: `selectByRect` takes WHOLE features, so a building straddling the tile edge pulls the selection's convex hull past the box — measured at **617 × 586 m for a 512 m pick**, which the tiler then charges **nine** jobs for instead of one. The hull of the selected buildings is simply not the area the user picked, and no tolerance closes a 105 m gap. `services/single_tile_selection` therefore holds the box, and the toolbar toggle mirrors it through `subscribe()` so nothing has to remember to keep the two in step. Submitting a simulation ends the mode and clears the map highlight **together** — clearing one without the other is what left an armed tile invisible, and then a forgotten pick silently shrank a later ground-material fetch. A ground-material fetch does NOT end it: it is preparation for a run on the same tile.

- **[2026-09-29]** [visualization/legend] A `QgsColorRampShader` of type **Discrete** colours a pixel with the FIRST item whose value is `>=` the pixel's — so a pixel **above the last item matches nothing and is drawn transparent**, which reads as white over the canvas. This is not a rounding artefact: the backend's `min-legend`/`max-legend` is a **display recommendation, not the data range**, so a UTCI run legended 21–30 over a grid reaching 31 dropped **15% of its valid pixels — the hottest ones** (open sun, water), exactly what the map is read for. **Fix:** `color_ramp._build_color_ramp_items` now sets the last Discrete item's value to `inf`, computing its label first so the legend still names the real bound. `Interpolated` already clamps to the end colours and is left alone; categorical ramps are 1..N integers and cannot overflow. **Related, same commit:** the registry sends `steps` / `stepsNames` as explicit JSON **nulls** for several analysis types (`thermal-comfort-index` has both), and `.get(key, [])` only defaults on a MISSING key — reading them as `None` reached `len(None)`. Use `.get(key) or []`.

- **[2026-09-29]** [visualization/legend] The single-tile and area paths legended results **differently**, so the same scenario was not visually comparable between them. The area path takes `AreaResult.min_legend`/`max_legend` (the SDK aggregates them across tiles); the single-tile path downloads one job and never read the equivalent keys, falling back to the grid's own range. **Fix:** `sdk_single_tile.legend_from_result` reads them from the raw job result and the renderer applies the same three tiers as the area path (API → grid range → manual override). **The wire keys are kebab** (`min-legend`, `max-legend`); camelCase is accepted as a defensive fallback, mirroring the SDK's `_area/_merge_common.append_legends`. That reader matched camelCase ONLY for a whole release, so every area run reported `min_legend=None` and nobody noticed — falling back to the grid range looks perfectly reasonable. A legend that goes missing is silent by construction; test the keys.

- **[2026-07-13]** [auth/weather] The legacy weather endpoint `app.infrared.city/api/public/weatherfiles/{file}/data` validates API keys against its **own key registry**, separate from `api.infrared.city` — keys issued for the new API get HTTP 401 there even though every other plugin call works. **Fix:** `services/epw_query.py` now goes through the SDK weather client (`/v2/utils/weather/{id}/data/filter`), same host + key as everything else. If a single endpoint 401s while the rest of the plugin works, check which HOST it hits first.

- **[2026-07-13]** [weather/backend] The utilities-service weather filter (`_matches_time_range`) applies month / day / hour predicates **independently per field**, not as a linear calendar window. Consequence: a multi-month `TimePeriod` ending in a sub-31-day month (e.g. Sep→Nov, `end_day=30`) silently drops day-31 rows of the *earlier* months → weather-array length no longer matches the sun-vector count → API rejects the run ("DNI length != sun_vectors"). Also, the SDK `TimePeriod` validator forbids year-wrap (northern winter Dec→Feb). Both are handled by splitting into multiple periods in `epw_query._time_periods_from_time_frame` (verified bit-exact against the legacy contract for all 110 UI-producible time frames). Touch that translation only with the same verification.

- **[2026-07-31]** [qt6/packaging] **Never reintroduce a compiled Qt resource file.** Icons used to be addressed as `:/plugins/infrared_city_gis/icons/...`, resolved by a `pyrcc5`-generated `resources.py` that `infrared_city_gis.py` imported at load. That module starts with `from PyQt5 import QtCore`, so on QGIS 4 (Qt6, no PyQt5 present) the plugin failed at **import time** — before any of its own code ran. It also could not be regenerated: **PyQt6 ships no resource compiler**, there is no `pyrcc6`. `resources.py`/`resources.qrc` are gone; icons load from disk via `_icon(name)`, which works on Qt5 and Qt6 alike and needs no build step. `pb_tool.cfg` `resource_files:` and the Makefile's `COMPILED_RESOURCE_FILES`/`pyrcc5` rule were emptied to match — if a QGIS plugin template ever re-adds them, don't.
- **[2026-07-31]** [qt6] Qt6 removes **every unscoped enum member**: `Qt.Checked` → `Qt.CheckState.Checked`, `QLineEdit.Password` → `QLineEdit.EchoMode.Password`, `QMessageBox.Yes` → `QMessageBox.StandardButton.Yes`, `QPainter.Antialiasing` → `QPainter.RenderHint.Antialiasing`, `Qt.transparent` → `Qt.GlobalColor.transparent`. The scoped spelling also works on PyQt5, so this is a one-way fix needing no version branching. **Grepping for these does not work** — four successive sweeps each missed a class of them: `Qt.*` alone misses widget-class enums (`QLineEdit.*`), an uppercase-first regex misses colour constants (`Qt.transparent` is lowercase), `is` comparison on sip enum objects silently finds nothing (they are int *subclass* instances — compare with `==`, or better, read `type(value).__name__`, which IS the scoped enum name), and resolving names against only `QtCore`/`QtGui`/`QtWidgets` misses `QtNetwork` (`QNetworkRequest.HttpStatusCodeAttribute` → `.Attribute.HttpStatusCodeAttribute`, which breaks **every** HTTP call the plugin makes through `services/qgis_http.py`). Enumerate the modules from the code (`grep -o 'qgis\.PyQt\.Qt[A-Za-z]*'`) rather than assuming.
- **[2026-08-06]** [qt6/tooling] `scripts/check_qt6_names.py` is the automated form of the sweep below — it parses the source with `ast` (so comments and docstrings cannot cause false failures), collects every Q-prefixed dotted access, and resolves each against a real binding. CI runs it against PyQt6 on every pull request (`lint.yml`, job `qt6-names`); `--binding pyqt5` checks the QGIS 3.44 side. It reports the QGIS classes it could **not** cover (`Qgis`, `Qgs*` — those need a QGIS install) rather than passing silently. Verified against the real bugs from this migration: it fails on `Qt.Checked` and `QLineEdit.Password`, exit 1. It cannot catch call-signature mismatches — the `pushMessage(level=0)` break was a wrong argument *type*, not a missing name.
- **[2026-08-03]** [qt6/tooling] **Verify names against the bundled interpreter instead of guessing.** QGIS ships its own Python; on macOS `/Applications/QGIS-<ver>.app/Contents/MacOS/python3.12` runs headless with `PYTHONPATH=<app>/Contents/Resources/python3.12{,/lib-dynload,/site-packages}:<app>/Contents/Resources/python` (PYTHONHOME does **not** work — the stdlib sits at `Resources/python3.12`, not the `Resources/lib/python3.12` the interpreter derives). That gives real `PyQt6` **and** `qgis.core`, so every name the plugin uses can be resolved on both bindings before shipping — which is how the QVariant break below was caught after two hand sweeps had cleared it.
- **[2026-08-03]** [qt6] `QVariant.Int` / `.String` / `.Double` **break on Qt6 — and so does the scoped `QVariant.Type.Int`**: PyQt6 drops the type constants entirely, so `QgsField("id", QVariant.Int)` fails at runtime. Use `QMetaType.Type.Int` / `.QString` / `.Double` (note `String` → **`QString`**), which exist on PyQt5 and PyQt6 alike, and which QGIS has preferred since 3.38. The `QVariant` *class* itself survives, so `isinstance(value, QVariant)` in `geotiff.py` is fine. Verified fine and left alone: `QgsWkbTypes.PolygonGeometry` / `.PointGeometry` (deprecated since 3.30, still present in 4.2) and `from qgis.PyQt.QtWidgets import QAction` (Qt6 moved `QAction` to `QtGui`, but the shim re-exports it into `QtWidgets`).

## Reviewer Corrections

_Deliberate deviations from `ir-dev:conventions`. The auto PR reviewer reads this
section — record it here rather than re-arguing it on every PR._

- **[2026-08-18]** [naming] **Python modules are `snake_case`, not the kebab-case
  `ir-dev:conventions` specifies for files.** `import infrared-city-gis` is a syntax
  error, so a QGIS plugin package has no choice: the folder is `infrared_city_gis/`
  and every module under it follows. The convention's intent (consistent, readable
  filenames) is met; only the separator differs. `scripts/` follows the same
  separator on purpose (`run_qgis_tests.sh`, `check_qt6_names.py`) — one rule for
  the whole repo beats a boundary nobody remembers. Docs and workflows are
  kebab-case as the convention specifies.
- **[2026-08-18]** [logging] **Log calls are prose with `%`-style args, not the
  structured key–value events `logging-conventions.md` requires.** The plugin does
  use `structlog`, but renders through `ConsoleRenderer` into a per-day file in the
  user's QGIS profile (`infrared_logger.py`) — it is never shipped to an aggregator,
  and nothing queries it. The reader is a human debugging their own install, or a
  user pasting a log into a support thread, so a readable sentence beats a
  machine-parsable event. The parts of that standard that **do** apply are followed:
  levels mean what the standard says, and secrets/PII stay out (`secret_manager.py`
  logs only the source a key came from, `sdk_payloads.py` logs an EPW basename
  rather than the full path). Revisit if these logs ever get collected centrally.

## Common QGIS Plugin Pitfalls (general — not yet hit here)

- **Don't `import requests` at module top-level if you might run inside QGIS server**: server profiles can have stripped Python. Wrap in a function-level import or guard with try/except.
- **`pb_tool zip` excludes files based on `.gitignore` only loosely**: always verify the ZIP contents before uploading to plugins.qgis.org.
- **`metadata.txt` `version=` must be SemVer** — plugins.qgis.org rejects non-semver tags.
- **`experimental=True`** keeps the plugin out of default search results until you flip it. Useful while iterating, but remember to flip when ready.
- **Plugin reload in QGIS doesn't always pick up `__init__.py` changes.** Use the *Plugin Reloader* community plugin or fully restart QGIS.
